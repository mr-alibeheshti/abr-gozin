# گزارش اصلاح، ارزیابی و دیپلوی جست‌وجوی ابرگزین

تاریخ: جمعه ۲۰۲۶-۱۱-۲۰ · ریپو: `github.com/mr-alibeheshti/abr-gozin` (branch `fix/search-eval`، merge‌شده در `main`) · محیط: https://abrgozin.ir

## ۱. خلاصه

- بررسی ۲۰ نوامبر ۷ خطای تأییدشده در جست‌وجوی زنده پیدا کرده بود: موقعیت منفی («خارج از ایران» → ایران)، خالی‌بودنِ بی‌توضیح برای VPS خارجی، ریال ۱۰ برابر، بودجهٔ بی‌واحد، اعداد حروفی، فروشگاه بدون کف منابع و ranking‌ای که پلن ضعیف‌تر و گران‌تر را بالاتر می‌آورد.
- اول harness ارزیابی ساختم (63 golden query، 91 query برچسب‌خورده برای intent) و «قبل» را روی production اندازه گرفتم: parse accuracy ‏41.9٪، check pass ‏64.4٪، 1130 Pareto violation.
- بعد از ۴ انتشار ابرگزین (F1–F10، منبع رسمی VPS خارجی، خواندن اندازهٔ بی‌واحد)، روی production: parse accuracy ‏100٪، check pass ‏100٪، Pareto violation صفر، zero-result ‏22.2٪ → 4.8٪ (هر سه مورد باقی‌مانده با `emptyReason`). سایت شخصی و رزومه هم با واقعیت‌های تأییدشده دیپلوی شد.

## ۲. روش

- **Golden set** (`eval/golden-queries.json`)، n = 63: ‏62 مورد با `expect` (فیلدهای parse‌شده) و 132 check. شامل ۷ خطا با ۲–۳ variant (F1: 10 + 5 نام provider دارای «ایران»، F2: 4، F3: 9، F4: 6، F5: 7، F6: 5، F7: 5) و 12 regression guard (کوئری‌هایی که کار می‌کردند، ي/ك عربی، ZWNJ، ارقام لاتین/فارسی، «تومن»، typo).
- **Runner** (`scripts/eval-search.mjs`): برای هر query ‏`GET /api/search?q=`، هر کدام ۵ بار. Metrics:
  - parse accuracy: درصد queryهایی که همهٔ فیلدهای `expect` درست است
  - check pass rate، با checkهای `nonEmpty`، `allWithinBudget`، `minDiskAtLeast`، `regionIs`، `typeIs`، `paretoConsistent` و `explicitEmptyReason`
  - zero-result rate
  - مجموع Pareto violations
  - latency p50/p95، شامل شبکه تا CDN
- **Pareto**: گروه A بر B غالب است اگر `A.min ≤ B.min`، روی هر منبع (cpu/ram/disk) که هر دو مقدار دارند A ≥ B، دست‌کم یک مقایسه strict باشد و دست‌کم یک منبع قابل مقایسه باشد. Violation یعنی B بالاتر از A رتبه بگیرد درحالی‌که A غالب است.
- **Intent set** (`eval/intent-labeled.json`)، n = 91: ‏vps 34، hosting 33 و none 24. شامل جمله‌های توصیفی بدون کلیدواژه و gibberish. زیرمجموعهٔ **model-only**، یعنی queryهایی که score مدل واقعاً نتیجهٔ جست‌وجو را عوض می‌کند (`needsIntentModel`)، ‏n = 58 است.
- «قبل» روی production، ایمیج `abrgozin:prod-20261020-f9856a1`، در 2026-11-20 13:59 UTC (۱۷:۲۹ تهران) اندازه‌گیری شد. «بعد» هم روی production، بلافاصله بعد از هر انتشار.
- محدودیت: golden set هم‌زمان با اصلاح‌ها نوشته شده است. پس ۱۰۰٪ یعنی «این ۶۳ مورد درست‌اند»، نه دقت عمومی parser. قدم بعدی یک hold-out set از queryهای واقعی است.

## ۴. اصلاح‌ها

### F1 — «خارج از ایران» و نام providerها
- **مسئله:** «سرور خارج از ایران» → `region=ir` و 79 گروه ایرانی. «ایران هاست» → `region=ir` و `type=hosting` → صفر نتیجه، چون IranHost در catalog فقط VPS دارد.
- **علت:** قاعدهٔ `ایران|داخلی` پیش از الگوی خارج اجرا می‌شد و «ایران» درون «خارج از ایران» و درون نام providerها هم match می‌شد.
- **تصمیم:**
  - الگوهای خارجی و منفی اول بررسی می‌شوند و به `eu` نگاشت می‌شوند، که تنها region خارجیِ schema است: «خارج از ایران»، «خارج کشور»، «خارجی»، «غیر ایرانی»، «بیرون از ایران»، outside iran، non-iran، اروپا، آلمان، هلند، فنلاند و …
  - نام providerها با word boundary پیدا و قبل از تشخیص region و type از متن حذف می‌شوند.
  - providerی که در متن نام برده شده با intent مدل override نمی‌شود.
- **trade-off:** `eu` یعنی «اروپا»، نه کشور دقیق (catalog کشور ثبت نمی‌کند). آمریکا و ترکیه region ندارند (بخش ۷).
- **تست:**
  - unit: 11 عبارت خارجی، 6 نام provider، و اینکه «server iran» دیگر provider ‏Server.ir نیست
  - 15 golden

### F2 — VPS خارجی: empty state صادق و منبع رسمی
- **مسئله:** «سرور مجازی آلمان» → صفر نتیجه، بدون هیچ توضیحی.
- **علت:** catalog هیچ VPS خارج از ایران نداشت و API دلیل خالی‌بودن را برنمی‌گرداند.
- **تصمیم (empty state، همیشه):** فیلد `emptyReason` با این مقدارها:
  - `no-foreign-vps-in-catalog`
  - `budget-too-low`، همراه `emptyContext.cheapest`
  - `requirements-blocked`
  - `no-dedicated-in-catalog`
  - `no-match`

  UI پیام «در کاتالوگ فعلی، سرور مجازی خارج از ایران نداریم» را با دو اقدام یک‌کلیکی نشان می‌دهد:
  - «حذف فیلتر موقعیت»: مقدار تازهٔ `region=any`، که موقعیتِ داخل متن را نادیده می‌گیرد. `region=all` را عوض نکردم، چون UI همیشه آن را می‌فرستد.
  - «دیدن هاست‌های خارج»

  برای بودجهٔ کم، UI ارزان‌ترین گزینه را نشان می‌دهد و دکمهٔ افزایش سقف دارد.
- **تصمیم (منبع):** صفحهٔ رسمی وب‌رمز (`webramz.com/server/vps/germany`؛ «آلمان / فنلاند»، Hetzner). وب‌رمز از قبل در catalog بود. منبع شامل ۴ پلن HCVPS است: 1/1/20 تا 4/4/50، به قیمت 2,205,000 تا 4,844,000 تومان در ماه، با ترافیک نامحدود و یک IP.
- **trade-off:**
  - فعلاً فقط یک provider خارجی داریم.
  - parser سخت‌گیر است: اگر موقعیت، دیسک NVMe، IP یا ترافیک صفحه عوض شود خطا می‌دهد و دادهٔ قبلی حفظ می‌شود.
  - empty state برای catalogی که VPS خارجی نداشته باشد همچنان تست می‌شود.
- **تست:**
  - همهٔ کدهای `emptyReason`، `region=any` و «دیدن هاست‌های خارج»
  - parse fixture: قیمت، منابع، `eu`، لینک سفارش
  - رد شدن صفحه‌ای با موقعیت دیگر

### F3 — واحد پول
- **مسئله:** «سرور زیر ۲۰ میلیون ریال» → `maxPrice = 20,000,000` تومان (۱۰ برابر).
- **علت:** regex بودجه ریال، K/M و triggerهای «کمتر از»، «نهایتاً» و «ماهی» را نمی‌شناخت.
- **تصمیم:**
  - ریال ÷10، تومان/تومن ×1، هزار/K ×1e3، میلیون/ملیون/M ×1e6
  - عددی که بعد از «تا» یک منبع یا مدت است بودجه حساب نمی‌شود: «تا ۴ گیگ رم»، «تا ۳ ماه»، «تا ۵ سایت»
- **تست:** جدول work order و 9 golden.

### F4 — بودجهٔ بی‌واحد
- **مسئله:** «هاست زیر ۵۰۰» → 500 تومان → صفر نتیجه.
- **علت:** عدد بی‌واحد همیشه تومان فرض می‌شد.
- **تصمیم:**
  - عدد ≥ 10,000 تومان است.
  - عدد کوچک‌تر دو نامزد ×1e3 و ×1e6 دارد. نامزدی برنده است که در بازهٔ min…max برآورد ماهانهٔ catalog زنده برای همان نوع سرویس باشد؛ اگر هر دو باشند، ×1e3.
  - اگر هیچ‌کدام در بازه نباشد: n ≥ 20 → ×1e3، وگرنه ×1e6.
  - پاسخ API فیلدهای `intent.budgetAssumed`، `budgetUnit` و `budgetText` را دارد.
  - chip «تا ۵۰۰٬۰۰۰ تومان در ماه (برداشت از عبارت)» با کلیک فیلتر بودجه را باز می‌کند.
  - «۲۰۰ تومن» محاوره‌ای (عدد کمتر از ۱۰۰۰ همراه تومن) هم همین قاعده را می‌گیرد.
- **trade-off:** «سرور زیر ۳۰» → 30 میلیون، چون 30 هزار زیر ارزان‌ترین VPS است. این یک فرض است، ولی شفاف و قابل ویرایش.
- **تست:** جدول work order، «سرور زیر ۳۰»، قاعدهٔ fallback با یک catalog مصنوعی، و اینکه `maxPrice` صریح برنده است.

### F5 — اعداد حروفی
- **مسئله:** «سرور زیر دو میلیون» → بودجه بی‌صدا حذف می‌شد و همهٔ 79 گروه برمی‌گشت.
- **علت:** parser فقط رقم را می‌شناخت.
- **تصمیم:**
  - یک parser کوچک عدد حروفی پیش از استخراج اجرا می‌شود: یک…نه، ده…نوزده، بیست…نود، صد…نهصد (با پونصد)، «نیم»، «و»، هزار و میلیون.
  - فقط دنباله‌ای که «مقدار» است تبدیل می‌شود: scale دارد، بعدش واحد آمده یا قبلش trigger بودجه است. این‌طور «نه» و «سی پنل» دست نمی‌خورند.
  - برای RAM و CPU هم کار می‌کند («چهار گیگ رم»، «دو هسته»).
- **تست:** جدول work order، «دو میلیون و پانصد هزار»، «یک میلیون و نیم»، «بیست و پنج گیگ دیسک»، و اینکه «… هزار و ۲ گیگ رم» با هم ادغام نمی‌شوند.

### F6 — فروشگاه بدون کف منابع
- **مسئله:** «هاست برای سایت فروشگاهی» → نتیجهٔ اول یک هاست 0.1 گیگابایتی به قیمت 12,417 تومان بود (MehrHost ECO-F طبق بررسی؛ در اندازه‌گیری «قبل» هم تأیید شد).
- **علت:** «فروشگاهی» بدون کلمهٔ وردپرس هیچ workload یا scenarioای نمی‌ساخت.
- **تصمیم:**
  - فروشگاهی، فروشگاه اینترنتی/آنلاین، shop، store و ecommerce → `wordpress/store` (کف 10GB دیسک و 2GB RAM)
  - وبلاگ و سایت خبری/محتوایی → `blog`
  - سایت شرکتی → `business`
  - فقط وقتی نوع سرویس hosting یا نامشخص است اعمال می‌شود، و workload صریح کاربر همیشه برنده است.
- **تست:** 10 عبارت، golden با `minDiskAtLeast:10`، و اینکه «storage» به معنی store نیست.

### F7 — ranking ناسازگار با Pareto (مهم‌ترین)
- **مسئله:** برای «سرور ایران برای داکر با ۴ گیگ رم زیر ۲ میلیون»، پلن 4/4/60 به قیمت 882,000 در رتبهٔ ۶ و پلن 2/4/40 به قیمت 1,590,000 در رتبهٔ ۲ بود. روی کل golden set ‏1130 violation وجود داشت.
- **علت:** مرتب‌سازی اصلی proximity بود (`Σ log2(actual/required)`) و قیمت فقط tie-breaker.
- **تصمیم:**
  - ترتیب پیش‌فرض: ارزان‌ترین گروهی که همهٔ شرط‌ها را دارد، بعد منابع بیشتر (cpu، ram، disk)، بعد `id`.
  - در قیمت‌های برابر، `paretoOrder` اجازه نمی‌دهد گروهِ مغلوب بالاتر از گروهِ غالب بیاید.
  - proximity به‌صورت `sort=fit` («نزدیک‌ترین به نیاز») باقی ماند.
  - لینک‌های قدیمی `price-desc`، `providers` و `ram` همان ترتیب قبلی را می‌دهند.
- **اکنون روی production:**
  - پیش‌فرض: 4/4/60@882,000 → ‏#1، 8/8/120@1,588,500 → ‏#6، 2/4/40@1,590,000 → ‏#7
  - با `sort=fit` دقیقاً همان #2/#6/#14 بررسی ۲۰ نوامبر بازتولید می‌شود.
- **trade-off:** کاربری که «هم‌اندازه» می‌خواهد باید `fit` را انتخاب کند. تست‌های قدیمیِ ترتیب حذف نشدند: حالا هم ترتیب جدید و هم ترتیب `fit` را چک می‌کنند.
- **تست:**
  - اعداد دقیق repro
  - invariant «صفر violation» روی همهٔ golden queryها (با دو تنظیم traffic/IP) و روی کل catalog
  - ۲۰۰ دور تست تصادفی با قیمت‌های برابر

## ۵. تصمیم ranking

- هدف کاربر «ارزان‌ترین پلنی است که نیازم را کامل برآورده کند». همهٔ گروه‌های فهرست از قبل همهٔ شرط‌ها را دارند (حداقل منابع، کف workload، بودجه، موقعیت). پس بین آن‌ها قیمتِ برآوردی معیار اول است، و در قیمت برابر منابع بیشتر مزیت است.
- proximity حذف نشد. برای کسی که نمی‌خواهد منابع اضافه بخرد یا مقایسهٔ هم‌اندازه می‌خواهد معنا دارد، پس گزینهٔ صریح `sort=fit` است و لینک‌های قدیمی هم کار می‌کنند.
- **invariant:** در ترتیب پیش‌فرض هیچ گروهی بالاتر از گروهی که بر آن غالب است نمی‌آید. چون مرتب‌سازی با `min` صعودی است، violation فقط در قیمت‌های برابر ممکن است و `paretoOrder` آن را برطرف می‌کند. تنها استثنا وقتی است که منابع جزئاً ناشناخته باشند و چرخهٔ غلبه بسازند؛ این حالت در داده رخ نداد. این invariant روی golden set و کل catalog تست می‌شود.

### trade-off و شکاف‌ها
- «سرور خارج از ایران» و «سرور خارجی» هنوز به `eu` نگاشت می‌شوند (golden F1). پس ترکیه، آمریکا، کانادا و امارات فقط با نام کشور یا گزینهٔ «سایر کشورها» می‌آیند.
- پلن‌های چندکشوری (Server.ir، AzarOnline، شناسه‌های مشترک IranServer) در جست‌وجوی منطقه‌ای چند بار دیده می‌شوند، هر بار با کشور خودش. این طبق صفحه‌های رسمی درست است، ولی شلوغ می‌کند.
- container قدیمی `abrgozin` همان SQLite را می‌خواند و حالا پلن‌های خارجی را هم می‌بیند (بخش ۷).
- چند query هنوز موقعیت نمی‌سازند: نام دیتاسنتر («هتزنر»، «OVH»)، مخفف «us»، و دو کشور در یک query («ایران یا آلمان» فقط آلمان را اعمال می‌کند).

### queryهایی که فردا بهتر است زنده امتحان نشوند
- «سرور هتزنر» یا «سرور us»: موقعیت نمی‌سازند و همهٔ VPSها را نشان می‌دهند.
- «سرور ایران یا آلمان»: فقط آلمان را اعمال می‌کند.
- «سرور خارجی» به‌عنوان نمونهٔ ترکیه یا آمریکا: فقط اروپا را نشان می‌دهد.
- «هاست ترکیه» و «هاست آمریکا» درست کار می‌کنند ولی خالی‌اند، با دلیل و اقدام. برای نمایش empty state خوب‌اند، نه برای نمایش نتیجه.
