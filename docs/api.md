# API contract

Outbound browser navigation adds `utm_source=abrgozin`, `utm_medium=referral`, `utm_campaign=hosting-comparison` and a placement-specific `utm_content`. `GET /go/:id` still returns 302 to the stored checkout URL with those tags added; unknown offers return 404. Existing checkout parameters and URL fragments are preserved. Internal links and stored/crawled provenance URLs remain unchanged.

All routes below are relative to `APP_BASE_PATH` (empty locally, `/abrgozin` in production). The build and runtime must use the same base path. The application redirects the unslashed base to its trailing-slash URL and preserves its query. API routes use JSON and the HttpOnly, SameSite=Strict browser session cookie scoped to this base path. `PUBLIC_URL` specifies the HTTPS origin permitted for state-changing requests and enables Secure cookies. Localhost origins remain allowed for local checks; any other Origin is rejected with 403. No external Postman workspace is published.

## GET /api/sources and GET /api/health

Both include a `job` object for the durable price worker: `{state, done, total, startedAt, finishedAt, nextRunAt, succeeded, failed, trigger, error, intervalHours: 72, enabled}`. Dates are ISO UTC strings or null; `trigger` is `manual` or `scheduled` or null. States are `idle`, `running`, `done` (one or more sources verified; inspect `failed` for partial failures), or `failed` (no sources verified or a fatal worker error). `enabled` indicates automatic scheduling in this server instance. A source's `checkedAt` changes on failure; its prior `verifiedAt` and offers remain intact.

The worker runs inside the Node server. SQLite stores its schedule, progress and a renewable lease shared with CLI/manual runs. A fresh schedule runs immediately unless `NO_REFRESH=1`; the latter only defers the first run when creating a new schedule. Existing overdue runs catch up after restart. Each completed attempt schedules the next for 72 hours after completion. An interrupted run can be reclaimed after its 120-second lease expires. `REFRESH_WORKER_ENABLED=0` disables automatic scheduling without removing manual refresh or the persisted schedule.

## POST /api/refresh

When `PUBLIC_URL` is configured, returns 403; production refresh is available only through the server CLI and automatic worker. Otherwise no body. Returns 202 with the running `job` snapshot after acquiring the database lease. The actual crawl runs asynchronously. Concurrent refreshes return 409 `{error}`; within 60 seconds after a completed attempt, returns 429 `{error}` with `Retry-After` in seconds. `npm run refresh` uses the same lease, cooldown and persistence. Scheduled runs and manual runs never intentionally overlap. Official pricing destinations and redirects are allowlisted; this endpoint accepts no caller-provided URL.

## GET /api/search

- `type`: `all` (default), `hosting` (includes WordPress), `vps`, or `dedicated`. Dedicated offers are a separate category; an empty catalog returns zero results.
- `provider`: optional provider ID, comma-separated IDs, or repeated query parameters, e.g. `provider=liara&provider=arvan`. Selected providers are ORed; all other filters remain binding. Unknown IDs return 400. An omitted provider selects all.
- `sort`: `price` or `price-desc`, ordering by each configuration's lowest estimated monthly cost. Offers within a configuration remain cheapest first. Legacy `providers` and `ram` links remain supported by the API.
- `scenario`: `general` or a scenario belonging to `workload`, as exposed by `/api/catalog.workloadGuide`; an incompatible scenario returns 400.
- `resourceMode`: `exact` (legacy default: selected cpu/ram/disk are equal, nearby results separate) or `minimum` (selected resources are binding lower bounds; no smaller nearby offers).
- Optional lower bounds `minDisk` (GB, 0–100000), `minRam` (GB, 0–4096), `minCpu` (0–1024). Optional `dataGB`, `growthGB` (0–100000), `backupCopies` (integer 0–30), `gpu` (`true`/`false`). Unspecified sizing values are unknown, not measured zero. Positive data adds ceil(base + (data + growth) × (1 + local backups) × 1.25) disk; 25% headroom is an explicit Abrgozin policy.
- Workload capacity floors apply before exact AND nearby results. Unknown required capacity cannot establish a match. GPU has no verified catalog data, so yields no matches. Official software requirements and Abrgozin starter policy are separately described by `requirements`. No fixed product/visitor capacity is asserted.
- WordPress uses a starter policy of 5GB disk / 1GB account RAM; store 10GB / 2GB. Known raw-server workloads use an Ubuntu cloud baseline of 25GB disk / 1GB RAM, with actual app consumption additional. These are shortlist floors, not compatibility or performance guarantees. All-workloads browsing preserves the catalog.
- Existing `q`, `workload`, `region`, `cpu`, `ram`, `disk`, `maxPrice`, `traffic`, `ip`, and `saved` retain their semantics.
- Response: `{groups, similarGroups, similarTotalGroups, resourceFilters, totalOffers, intent, filters, requirements, model}`. Similar results still rank resource proximity first, then the selected price ordering. Invalid filters: 400 `{error}`.

## GET /api/chat/status

Returns `{configured, provider: "Gemini", model, message, timeoutMs, transport}`. `transport` is `direct`, `http-proxy`, or `cloudflare-ai-gateway`. `timeoutMs` is the total upstream deadline, including a bounded retry (20 seconds by default). `configured` means a server key and any selected gateway settings are present and valid, not that upstream access or quota has been verified. Never returns keys, tokens or gateway URLs.

Optional Cloudflare provider-native routing uses the paired server-only variables `GEMINI_GATEWAY_URL` and `GEMINI_GATEWAY_TOKEN`; see [setup](cloudflare-gateway.md). It bypasses `GEMINI_PROXY_URL` and `GEMINI_BASE_URL`. Invalid or incomplete gateway settings disable chat instead of silently using another route. Production gateway URLs must use HTTPS on `gateway.ai.cloudflare.com` with the Google AI Studio provider path; HTTP loopback URLs are permitted for local contract simulations. Gateway headers disable caching, log collection, gateway retries and Cloudflare billing fallback. The app retains its bounded transient retry and cancellation; in gateway mode the default attempt deadline uses the full remaining shared deadline, rather than discarding a slow response after ten seconds. Gemini output and eligibility rules remain identical. Gateway setup alone does not establish availability from a particular region.

Gateway requests authenticate to Google with the server-side `key` query parameter: the live gateway rejected header-only provider credentials with Cloudflare error 2044. Direct/proxy requests continue to use `x-goog-api-key`. Credential-bearing request URLs and upstream error bodies must never be logged or exposed to the browser.

## POST /api/chat

Request: `{messages: [{role: "user"|"assistant", content: string}], filters?: object, needs?: {purpose, quantity, storage, load, features}}`.

Messages must alternate starting and ending with a user; 1–15 messages, each nonempty and at most 4000 characters (user input at most 2000), combined at most 16000. Send only the conversation, never a system role or a catalog. `filters` accepts the search filters plus boolean `ip`; saved session data is excluded from the model context.

The server sends the conversation, a summary of supported workloads and catalog availability, at most twelve relevant catalog rows, and current filters/needs to Gemini. Full sources and software compatibility checks remain server-side. The server searches the entire live catalog after the model extracts the user's filters, so the prompt shortlist does not limit results. It does not send cookies, saved selections, or credentials in the prompt. Chat history remains in browser memory and is not persisted in SQLite.

Response: `{reply, filters, needs, assessment, canApply, recommendations, provider, model, catalogCount}`. `needs` fields are nullable summaries of explicit user answers; an explicit unknown answer counts as answered and must not be guessed. `assessment` contains `ready`, `pending` questions, and researched `requirements`. Before offers, each known workload requires a specific scenario, all five needs, and an explicit budget. Ambiguous colloquial budgets such as “۵۰۰ تومن” must be clarified. Recommendations and apply actions are gated until ready and consultation intent; greetings and explanations have no apply action. Model attempts to recommend early or below the sizing floor are filtered by the server. `filters` contains `type`, `workload`, `region`, `provider` (ID array), nullable `ram`/`cpu`/`disk`/`maxPrice`, `sort`, `traffic`, and boolean `ip`. Applying these filters requires the user's button click. `recommendations` contains at most three verified catalog offers matching the returned filters; all prices and links are computed by the server, never accepted from the model. Recommendation `href` values include `APP_BASE_PATH` before `/go/:id`. Model output with unknown offer IDs or invalid filters is rejected.

During incomplete consultation, `reply` is the first pending question in one short sentence; the form still receives every unanswered field. A known WordPress workload asks for the site category (store, news/blog, or business) rather than asking for its technology again. News/content sites use the existing `blog` scenario. Once the category is answered, the next question advances to the remaining needs. The form uses workload-specific labels and examples, including “نوع سایت” for WordPress.

Errors: `{error, code}`. 400 `INVALID_CHAT_REQUEST`; 429 `CHAT_RATE_LIMIT` (Retry-After); 503 `AI_NOT_CONFIGURED`; 502 `AI_AUTH_ERROR`, `AI_UPSTREAM_ERROR`, or `AI_INVALID_RESPONSE`; 429 `AI_QUOTA_EXCEEDED`; 504 `AI_TIMEOUT`. There is one in-flight request per session, at most eight requests/minute/session, and at most four concurrent requests globally. Transient 408/500/502/503/504 and network/attempt-timeout failures get at most one retry with jitter, within the shared deadline. Auth, quota and invalid model output are not retried. Disconnecting/cancelling aborts upstream work and releases the session. No silent local or paid-provider fallback. Metadata-only logs record latency, prompt bytes, attempt count and outcome without conversation text or credentials.

Default provider: Gemini 3.5 Flash-Lite, which has a free tier subject to Google account, region, and quota eligibility. Use an unbilled/free-tier project for free usage. Authentication and structured generation follow the official docs: https://ai.google.dev/gemini-api/docs/api-key and https://ai.google.dev/gemini-api/docs/generate-content/structured-output . Orbit confirmed the generateContent JSON flow but its brief used an old model and omitted resilience controls. Current official Gemini REST and thinking docs define the header authentication and MINIMAL thinking configuration used here. Retry policy is implemented by this service.

`filters` also carries `scenario`, `resourceMode`, nullable sizing bounds/capacity fields and boolean `gpu`. The UI persists these fields in search links. `GET /api/catalog` includes `workloadGuide` and `sizingRevision`; `GET /api/search` includes `requirements` (minimum, rationale, calculation, checks, sources with reviewed date, conflicts, blockers, excludedOffers). Research and policy details: [workload-sizing.md](workload-sizing.md).

Redis and Python ML scenarios require an explicit/measured RAM bound (`ram` or `minRam`) before shortlisting. A disk-file size alone does not determine Redis memory. GPU requests remain blocked until verified hardware data exists.

Ready consultation summaries are generated by the server from validated recommendation count and assessment, so unconstrained model prose cannot claim a plan guarantees workload capacity. The configured default is Gemini 3.5 Flash-Lite ([official free-tier pricing](https://ai.google.dev/gemini-api/docs/pricing)); the previous 3.1 Flash-Lite repeatedly returned HTTP 503. Live 3.5 Flash-Lite completed a two-turn consultation after this change, including recovery from one 503. This does not guarantee upstream availability; no automatic provider/model fallback is configured.
